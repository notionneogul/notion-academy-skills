# 학원 템플릿 연결

이 스킬은 두 가지를 한다. **연결**(데이터베이스 14개를 찾아 `~/.academy/config.json` 에 저장)과, 연결 다음에 오는 **샘플 데이터 정리**(제작자가 넣어 둔 샘플 행을 `🗃️ 샘플 보관` 페이지로 치우기)다. 구매자가 첫날 이 둘을 이어서 한다.

먼저 `../academy-core/references/db-map.md` 를 읽는다. 지문표와 `~/.academy/config.json` 규격이 거기 있다.

## 연결 절차

1. 사용자에게 **복제한 템플릿 페이지 링크 하나**를 받는다. 원본 판매 페이지가 아니라 사용자 워크스페이스에 복제된 것이어야 한다.
2. `notion-fetch` 로 그 페이지를 읽고 블록 트리에서 `collection://` URL 을 모은다. 하위 페이지는 깊이 3까지 재귀한다. 깊이 3 은 실측 기준 가장 깊은 대상 DB 가 루트에서 깊이 2 라 여유 1 을 둔 값이다.
3. 같은 `collection://` URL 이 여러 번 나오면 하나로 접는다. 링크된 뷰가 원본과 같은 ID 를 쓰기 때문이다.
4. 각 데이터 소스를 `notion-fetch` 로 읽어 **지문표와 대조한다.** 이름이 맞아도 지문이 어긋나면 통과시키지 않는다.
5. 14개가 모두 확인되면 `~/.academy/config.json` 을 쓴다. 폴더가 없으면 만든다.
6. 사용자에게 확인 결과를 표로 보고한다. 데이터베이스명·행 수·확인 여부. 행 수는 `notion-query-data-sources` 로 `SELECT COUNT(*) FROM "collection://<uuid>"` 를 각 데이터 소스에 한 번씩 돌려 센다. 행을 전부 끌어와 세지 않는다.
7. 행 수가 제작자 샘플로 보이면(대부분의 DB 에 행이 차 있다) 「샘플 데이터 정리」를 이어서 할지 묻는다. **묻기만 하고 자동으로 시작하지 않는다.**

## 연결 실패 처리

| 상황 | 대응 |
|---|---|
| 링크가 열리지 않음 | 노션 커넥터에 그 페이지가 추가되지 않았을 가능성이 크다. 노션에서 페이지 우상단 `...` → `연결` → Claude 추가를 안내한다 |
| 14개 미만 발견 | 구매자가 페이지를 한 겹 더 감싸 두었을 수 있다. **먼저 깊이를 4로 늘려 다시 찾는다.** |
| 깊이를 늘려도 14개 미만 | 몇 개를 찾았고 무엇이 없는지 나열한다. 템플릿 버전이 낮거나 일부 DB 가 다른 페이지로 옮겨졌을 수 있다 |
| 지문 불일치 | 어느 DB 의 어느 속성이 어긋났는지 보고하고 멈춘다. 임의로 매칭하지 않는다 |
| 이미 연결되어 있음 | 기존 설정의 `root_page` 와 `connected_at` 을 보여주고 덮어쓸지 묻는다 |

## 샘플 데이터 정리

"샘플 지워줘", "샘플 데이터 정리해줘", "남의 데이터 치워줘" 로 들어온다. 연결이 끝난 직후가 보통이지만 나중에 따로 불러도 된다.

**「통째로 비우기」 한 가지 방식뿐이다.** 샘플 행을 전부 `🗃️ 샘플 보관` 페이지로 옮겨 DB 를 비운다. 이름만 실제 학생 이름으로 바꿔 재사용하는 방식은 제공하지 않는다 — 샘플 행에는 날짜·점수·상담 기록이 얽혀 있어 이름만 바꾸면 남의 기록이 내 학생의 기록으로 남는다.

`~/.academy/config.json` 이 없으면 즉시 멈추고 「연결 절차」를 먼저 안내한다.

### 시작 전에 읽는다

- `../academy-core/references/write-gate.md` — 쓰기 관문. **6단계 「보관 페이지 절차」에 `🗃️ 샘플 보관` 페이지를 찾고 없으면 만드는 절차가 있고, `notion-move-pages` 배치 상한(100건)도 거기 있다.** 그 절차를 그대로 따르고 여기서 다시 적지 않는다. 승인 판정은 4단계다. **5단계의 100건은 `notion-create-pages` 상한이라 이 스킬과 무관하다** — 이 스킬은 행을 만들지 않는다
- `../academy-core/references/write-safety.md` — 「행을 보관 페이지로 이동」은 일괄 승인 + 되돌리기 안내, 「보관 페이지 본문에 되돌리기 목록 쓰기」는 그 승인에 포함된다. 되돌리기의 `new_parent` 형식도 여기 있다
- `../academy-core/references/query-limits.md` — 행 수는 `COUNT(*)` 로 센다. **몇 행인지는 구매자마다 다르므로 이 문서의 숫자를 믿지 않고 매번 조회한다.** 「행이 많은 DB 는 통째로 읽지 않는다」가 이 스킬의 조회에 직접 걸린다
- `../academy-core/references/db-map.md` — DB 이름과 지문. **`collection://<uuid>` 의 실제 값은 여기가 아니라 `~/.academy/config.json` 의 `databases` 에 있다** — db-map 에 있는 것은 자리표시자다. 되돌릴 때 쓸 uuid 도 config 에서 얻는다

### 왜 지우지 않고 옮기나

**행을 삭제하는 도구가 없다.** 대신 행을 `🗃️ 샘플 보관` 페이지 밑으로 옮기면 DB 에서 사라지고, 되돌리면 날짜·select·relation 값이 전부 살아난다(실측 확인, 절차는 `../academy-core/references/write-safety.md` 「되돌리기 절차」). 그래서 이 작업은 **되돌릴 수는 있지만 규모가 큰** 작업이다.

`🗃️ 샘플 보관` 페이지는 대개 템플릿에 이미 들어 있다. 이름으로 찾고, 없을 때만 만든다. **페이지 id 를 문서나 기억에 박아 두지 않는다 — 구매자 사본마다 다르다.**

### 옮긴 행은 속성이 사라진다 — 그래서 목록을 남긴다

보관 페이지 밑으로 옮긴 행을 `notion-fetch` 로 열면 **`title` 하나만 나온다.** 출석 날짜도 출결상태도 `학생` relation 도 보이지 않는다. 노션이 title 을 「김서준 물리 지각」처럼 자동으로 채워 주지만 **그 행이 원래 어느 DB 것이었는지는 알려 주지 않는다.** 실측으로 확인된 동작이다.

되돌리기 메커니즘 자체는 멀쩡하다(위 「왜 지우지 않고 옮기나」). 문제는 **어느 DB 로 되돌릴지 아는 것**뿐이다.

그래서 **보관 페이지 본문에 「되돌리기 목록」을 적는다. 이 목록이 되돌리기의 유일한 근거다.** 기억에만 두지 않는다 — 세션이 끝나면 사라진다.

**기록이 이동보다 먼저다.** 옮긴 뒤에 적으면 마지막 `notion-move-pages` 와 `insert_content` 사이에 창이 생긴다. 그 창에서 실패하면 — 도구 오류든 세션 종료든 — 수백 행이 `title` 만 남은 채, 어느 DB 것인지 아는 근거 없이 놓인다. **한 배치를 옮기기 전에 그 배치의 id 를 먼저 적으면 그 창이 구조적으로 사라진다.**

**옮기지 못한 id 가 목록에 섞이는 것은 무해하다.** 그 행은 아직 원래 DB 에 있으므로 되돌릴 때 그리로 다시 옮겨도 **이미 제자리라 no-op 으로 지나간다**(아래 「되돌리기」). 위험한 것은 반대 방향 하나뿐이다 — **옮겼는데 목록에 없는 행.** 그것만은 되돌릴 수 없다.

기록은 `notion-update-page` 를 `command: "insert_content"` 로, `position` 은 `{"type": "end"}` 로 호출해 덧붙인다. 자세한 걸음은 아래 「DB 하나를 옮기는 루프」에 있다.

형식은 이대로 쓴다. `notion-fetch` 로 다시 읽으면 그대로 나오는 것을 실측으로 확인했다. **id 는 한 줄에 공백으로 이어 붙인다** — 한 줄에 하나씩 적으면 로그가 수천 행인 학원에서 본문이 감당이 안 된다. 이 형식이면 **줄 수가 행 수가 아니라 옮기는 DB 개수에 묶인다** — DB 하나가 제목 줄과 id 줄 두 줄로 끝나고, 옮기는 DB 는 12개(14개 중 남기는 2종을 뺀 수)다

```
### 되돌리기 목록

- 옮긴 날: <YYYY-MM-DD>
- 출석부 `collection://<uuid>` — <N>건
  `<id>` `<id>` `<id>` ...
- 과제 `collection://<uuid>` — <N>건
  `<id>` `<id>` ...
```

### 옮기는 순서 — 잎에서 뿌리로

**반드시 이 순서다.** 전부 비우고 나면 최종 상태는 순서와 무관하다 — 다 옮기고 나면 가리킬 것도 가리켜질 것도 없다. 순서가 실제로 의미를 갖는 곳은 둘이다. **중간에 멈췄을 때**와 **부분 정리**다. 잎에서 뿌리로 가면 어느 지점에서 멈춰도 「로그는 없고 명단은 남았다」는, 원장이 읽고 판단할 수 있는 상태다. 반대로 가면 로그 수백 행이 **사라진 학생을 가리킨 채** 방치된다.

| 단계 | 옮기는 DB | 왜 이 자리인가 |
|---|---|---|
| 1 | `출석부` · `과제` · `시험` · `수강료 납부` · `재원생 상담` · `클래스 공지사항` | 로그 6종. 잎이다 — 이 행들은 학생·클래스를 가리키기만 하고, 사라져도 남는 쪽에서는 relation 한 칸이 빌 뿐이다(아래 「남기는 것」 참고). 행이 가장 많은 단계이기도 하다 |
| 2 | `시험 카테고리` · `신입생` | 샘플 명단 2종. `시험` 이 `시험 카테고리` 를 가리키므로, 1단계에서 시험 행이 사라진 뒤라야 카테고리를 옮겨도 그것을 가리키는 행이 남지 않는다 |
| 3 | `학생 과목별 페이지` | 1·2단계 로그가 전부 이 DB 를 가리킨다. 먼저 옮기면 학생 없는 로그가 남는다 |
| 4 | `학생` | 과목 페이지가 학생을 가리킨다 |
| 5 | `클래스` · `학교` | 뿌리. 과목 페이지가 클래스를, 학생과 신입생이 학교를 가리킨다 |

각 단계의 대상은 그 DB 의 **모든 행**이다. 단계는 순서만 정한다 — 조회·기록·이동·재확인은 DB 하나씩 돈다. 실제 걸음은 아래 「DB 하나를 옮기는 루프」를 따른다.

### 남기는 것 2종 — 어떤 경우에도 옮기지 않는다

| DB | 왜 남기나 |
|---|---|
| `문자 양식` | 제작자가 만든 양식이 그대로 원장이 쓸 양식이다. 문구만 고쳐 쓴다 |
| `납부 월` | `2026년 1월` 같은 연월이라 학원이 달라도 그대로 재사용된다 |

### DB 하나를 옮기는 루프

**단위는 단계가 아니라 DB 다.** 「옮기는 순서」가 정한 차례대로, 옮기는 DB 12개마다 아래 다섯 걸음을 돈다.

1. **DB 를 정확히 고른다.** `~/.academy/config.json` 의 `databases` 키와 **정확히 일치**하는 이름으로 찾는다. 접두·부분 일치로 풀지 않는다 — `학생`/`학생 과목별 페이지`, `시험`/`시험 카테고리` 가 서로 접두사다. 부분 일치로 풀면 **`학생` 을 옮기려다 `학생 과목별 페이지` 가 딸려가거나 그 반대가 된다.** 대상 목록을 확정한 뒤 **남기는 2종이 그 안에 없는지 한 번 더 확인하고** 이동을 시작한다
2. **`COUNT(*)` 로 남은 행 수를 센다.** 0 이면 이 DB 는 끝이다
3. **id 를 한 배치만 조회한다.** `SELECT id FROM "collection://<uuid>" LIMIT 100`. **전량을 한 번에 끌어오려 하지 않는다** — `notion-query-data-sources` 는 SQL 모드에 페이지네이션이 없어 **결과가 잘려도 잘렸다는 신호를 주지 않고**, `query-limits.md` 「행이 많은 DB 는 통째로 읽지 않는다」가 그것을 금지한다. 1단계가 옮기는 로그 4종(출석부·과제·시험·수강료 납부)이 그 문서가 이름으로 든 DB 그대로다
4. **그 id 를 목록에 먼저 적고**(`insert_content`), **그다음** `notion-move-pages` 로 옮긴다. **순서를 바꾸지 않는다.** `notion-move-pages` 는 페이지 **uuid 배열**을 받으므로 조회한 id 를 그대로 넘긴다 — 목록에 적는 것도 같은 id 라 `url` 을 따로 뽑을 이유가 없다
5. **`COUNT(*)` 를 다시 센다.** 0 이 아니면 2번으로 돌아간다. 두 번 돌았는데 수가 줄지 않으면 멈추고 보고한다

**마지막 `COUNT(*)` 가 0 인 것이 그 DB 를 다 옮겼다는 유일한 증거다.** 잘린 조회로 절반만 옮기고도 「N행 옮겼습니다」로 보고하는 일을 이 재확인이 막는다. 0 이 아닌 채로 끝났으면 결과 보고에 **어느 DB 에 몇 행이 남았는지** 적는다.

**「출석부만 비워줘」 같은 부분 정리도 이 루프를 그대로 탄다.** 단계가 없다고 목록 기록을 건너뛰지 않는다 — 단독으로 옮긴 행도 목록에 없으면 되돌릴 수 없다.

### 반드시 알려야 할 부작용

**3단계에서 `학생 과목별 페이지` 를 전부 치우면 `문자 양식` 의 `학생` relation 이 전부 빈다.** `문자 양식` 은 남기지만 그 안의 학생 연결은 과목 페이지를 가리키고 있었기 때문이다. 원장이 나중에 학생을 등록해도 양식에 연결해 두지 않으면 `academy-message` 가 그 학생을 대상에서 빼거나 경고한다.

**이것은 스키마에서 따라 나오는 추론이고 실측으로 확인하지는 않았다** — `문자 양식` 의 `학생` 은 과목 페이지를 가리키는 relation 이므로 대상이 사라지면 빈다는 것이 근거다(`db-map.md` 「이름이 오해를 부르는 relation」). 원장에게는 그대로 알리되, 정리 뒤 노션 화면에서 한 번 확인하도록 안내한다.

이 사실은 **승인을 받기 전 미리보기에 한 번, 결과 보고에 한 번** 적는다. 결과 보고에서 빠뜨리면 원장은 문자가 안 나가는 이유를 몇 주 뒤에 알게 된다.

### 주의

버튼이 있는 DB(`학생` 의 `퇴원`, `신입생` 의 `재원생 등록`)의 행도 같은 방식으로 옮긴다. 버튼은 데이터베이스에 붙어 있어 행을 옮겨도 남지만, **실제 동작은 확인되지 않았다.** 되돌린 뒤 버튼이 정상인지는 원장이 노션 화면에서 한 번 확인하도록 안내한다.

### 관문

`write-gate.md` 의 관문을 따르되 이 작업 고유의 것은 다음 넷이다.

**1. 미리보기는 DB별 행 수 표다.** 행을 한 줄씩 보여주지 않는다 — 수백 행을 나열해도 원장이 검토할 수 있는 것이 아니다. 표는 옮기는 순서대로 놓고, 남기는 2종을 아래에 따로 붙여 **무엇이 남는지도 같이 보이게** 한다. 행 수는 이 자리에서 `COUNT(*)` 로 세어 넣는다.

```
샘플 데이터 전체를 `🗃️ 샘플 보관` 페이지로 옮깁니다.

| 단계 | 데이터베이스 | 행 |
|---|---|---|
| 1 | 출석부 · 과제 · 시험 · 수강료 납부 · 재원생 상담 · 클래스 공지사항 | <조회한 수> |
| 2 | 시험 카테고리 · 신입생 | <조회한 수> |
| 3 | 학생 과목별 페이지 | <조회한 수> |
| 4 | 학생 | <조회한 수> |
| 5 | 클래스 · 학교 | <조회한 수> |

남기는 것: 문자 양식 · 납부 월

⚠️ 과목 페이지를 치우면 문자 양식의 `학생` 연결이 전부 빕니다.

샘플 데이터 전체를 치웁니다. 되돌릴 수 있지만 규모가 큽니다. 진행할까요?
```

**2. 승인 문구를 약하게 쓰지 않는다.** 마지막 줄은 「샘플 데이터 전체를 치웁니다. 되돌릴 수 있지만 규모가 큽니다. 진행할까요?」다. 승인의 판정 기준은 `write-gate.md` 4단계다 — 침묵은 승인이 아니다.

**3. 한 번에 하나씩, 기록하고 옮기고 확인한다.** 1단계부터 순서대로, DB 하나씩 위 「DB 하나를 옮기는 루프」를 돈다. **기록이 이동보다 먼저다.** DB 하나가 끝날 때마다 **몇 행을 옮겼는지와 `COUNT(*)` 재확인 결과를 말하고** 다음으로 간다. 열둘을 한 덩어리로 돌려 놓고 마지막에 한 번 쓰거나 보고하지 않는다.

**보고는 DB 하나당 한 줄로 묶는다.** 배치마다 보고하면 수십 줄이 되어 원장이 읽지 않는다 — 행이 많은 DB 는 `LIMIT 100` 배치가 여러 번 돈다는 것을 한 줄 안에 담는다.

> 출석부 <N>행 → 2회에 나눠 옮김, 남은 행 0

**4. 중간에 실패하면 어디까지 갔는지 정확히 말하고 멈춘다.** 어느 DB 의 몇 번째 배치에서 멈췄는지와 그 DB 의 마지막 `COUNT(*)` 를 적는다. 기록이 이동보다 앞서므로 **옮긴 것은 이미 목록에 있다** — 옮기지 못한 id 가 목록에 섞여 있어도 되돌릴 때 no-op 으로 지나간다. **조용히 다음 DB 로 넘어가지 않는다.** 넘어가면 그 시점의 DB 상태가 무엇인지 아무도 모르게 된다.

> 3단계에서 멈췄습니다. 1·2단계(로그 6종, 명단 2종)는 전부 옮겼고 각 DB 의 `COUNT(*)` 가 0 인 것을 확인했습니다. 3단계 `학생 과목별 페이지` 는 17행 중 5행까지 옮긴 뒤 실패했습니다(남은 12행). 학생·클래스·학교는 손대지 않았습니다.

### 결과 보고

DB별로 옮긴 행 수와 마지막 `COUNT(*)` 를 보고하고, 부작용과 되돌리기 안내를 **반드시 함께** 적는다. 0 이 아닌 채 끝난 DB 가 있으면 그것부터 적는다.

**보관 페이지를 지우라는 안내는 샘플 정리 직후에만 한다.** 이 페이지는 여덟 쓰기 스킬의 「방금 거 취소해줘」도 같은 곳으로 옮기는 **공용 보관소**다(`write-gate.md` 6단계). 몇 주 뒤 이 안내를 기억한 원장이 지우면 그동안 쌓인 취소분까지 없앤다 — 그래서 안내에 **지우기 전에 내용을 확인하라**는 조건을 함께 붙인다.

```
샘플 데이터를 `🗃️ 샘플 보관` 페이지로 옮겼습니다. (DB별 행 수, 전부 COUNT 0 확인)
되돌리기 목록을 보관 페이지에 적어 두었습니다.

⚠️ 문자 양식에 연결된 학생이 전부 비었습니다. 새 학생을 등록한 뒤
노션에서 각 양식의 `학생` 속성에 연결해 주세요.

확인이 끝나고 되돌릴 일이 없으면 `🗃️ 샘플 보관` 페이지를 지우셔도 됩니다.
다만 이 페이지는 다른 작업의 「방금 거 취소해줘」도 함께 쓰는 곳이라,
지우기 전에 안에 샘플 말고 다른 것이 들어 있지 않은지 확인해 주세요.
⚠️ 지우면 되돌리기 목록도 함께 사라져 되돌릴 수 없습니다.

이제 실제 학생을 넣을 차례입니다. "신입생 OO 등록해줘" 라고 말씀하시면
`academy-enroll` 이 이어받습니다.
```

### 되돌리기

"샘플 되돌려줘" 로 들어온다. 보관 페이지 밑의 행을 원래 DB 로 되돌린다.

**보관 페이지의 상태를 읽지 않는다.** 자식 목록을 조회하지도, 목록과 대조하지도 않는다. **이미 제자리에 있는 행을 다시 `notion-move-pages` 하는 것은 오류가 아니라 무해한 no-op 이고, 몇 건이 그랬는지 도구가 직접 알려준다** — 실측 응답이 `1 item was already in the target location: <uuid>` 였다.

그래서 「이미 되돌아갔는지」를 **추론하지 않는다. 추론이 없으니 틀릴 수도 없다.** 자식 목록을 안 읽으니 그 목록이 잘릴 걱정도, 대시 있는/없는 uuid 를 맞추는 정규화도 필요 없다(`notion-move-pages` 는 대시 유무를 가리지 않는다). 부분 되돌리기를 두 번 하든 원장이 노션에서 직접 몇 개를 되돌려 놓았든 결과는 같다 — **상태를 읽지 않고 목적 상태를 선언하는 방식**이라 몇 번을 돌려도 같은 자리에 놓인다.

1. **보관 페이지 본문에서 「되돌리기 목록」만 읽는다**(`notion-fetch`). DB 줄 아래 한 줄에 id 가 공백으로 이어져 있으니 **공백 기준으로 잘라** 읽는다
2. **목록의 id 를 DB 별로, 이동의 역순으로, 100건씩** `notion-move-pages` 한다
3. **도구가 돌려주는 결과를 그대로 읽는다** — 되돌린 건수와 `already in the target location` 건수
4. **결과 보고에 둘 다 적는다** — 「<N>건을 되돌렸습니다. <M>건은 이미 제자리에 있었습니다」

**순서는 반대다 — 뿌리에서 잎으로.** `클래스`·`학교` → `학생` → `학생 과목별 페이지` → `시험 카테고리`·`신입생` → 로그 6종. 잎을 먼저 되돌리면 아직 돌아오지 않은 뿌리를 가리키는 상태가 된다.

되돌리는 호출 형식(`new_parent` 에 `data_source_id` 를 주는 법, `collection://` 접두어를 떼는 것)은 `../academy-core/references/write-safety.md` 「되돌리기 절차」를 그대로 따른다.

**되돌릴 때도 배치 상한은 같다.** `notion-move-pages` 는 한 번에 100건까지다(`write-gate.md` 6단계). 나눠 부르고 **배치마다 도구 응답을 읽어** 되돌린 건수와 이미 제자리였던 건수를 누적한다.

**목록이 없으면 되돌릴 수 없다고 정직하게 말하고 멈춘다.** 옮긴 행에는 title 밖에 남지 않아 어느 DB 것인지 알아낼 방법이 없다. 추측으로 아무 DB 에나 넣지 않는다 — 잘못 넣으면 relation 이 엉키고, 그것은 이번엔 되돌릴 수 없다. 목록이 중간까지만 있으면 **적혀 있는 데까지만** 되돌리고, 나머지는 되돌릴 수 없다고 그대로 보고한다.

되돌리기도 쓰기다. **미리보기는 목록 기준이다** — 「목록에 <N>건이 있습니다. 되돌릴까요?」. 실제로 몇 건이 움직일지는 옮겨 봐야 알고, 그것을 미리 알려고 상태를 읽는 순간 위에서 없앤 대조가 되살아난다. 승인 판정은 `write-gate.md` 4단계를 그대로 따른다. 전부 되돌린 뒤에는 보관 페이지를 지워도 된다고 안내한다.

## 하지 않는 것

- **연결 단계는 노션에 아무것도 쓰지 않는다.** 읽기와 로컬 파일 저장뿐이다
- **샘플 정리는 행을 옮기고, 보관 페이지 본문에 되돌리기 목록을 적을 뿐이다.** DB 행을 지우거나 행의 값을 고치지 않는다. `write-safety.md` 의 「DB 휴지통 이동」은 금지다
- 남기는 2종(`문자 양식` · `납부 월`)은 원장이 따로 요청해도 이 절차로 옮기지 않는다
- 속성을 추가하거나 이름을 바꾸지 않는다
- 지문이 어긋난 DB 를 추측으로 매칭하지 않는다
- 샘플 정리를 승인 없이 시작하지 않는다. 연결이 끝났다고 이어서 돌리지 않는다

발화 예시는 `references/examples.md` 를 본다.
