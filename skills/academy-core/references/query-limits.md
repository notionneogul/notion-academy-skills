# query-limits.md — 노션 쿼리 도구 제약

노션 데이터베이스를 조회하는 모든 `academy-*` 스킬이 **조회를 시작하기 전에** 읽는다. 여기 적힌 제약을 벗어난 쿼리는 오류로 거부되거나, 더 나쁘게는 조용히 틀린 답을 낸다.

## 쿼리 도구 제약 (실측)

아래는 실제 노션 쿼리 도구에 돌려서 확인한 제약이다. 검사나 조회를 추가할 때도 이 다섯 가지를 벗어나지 않는다.

| 제약 | 내용 |
|---|---|
| JOIN 금지 | 어떤 형태의 JOIN도 안 된다. `Only a single SELECT query against the provided collection views is permitted` 로 거부된다. 여러 DB를 엮는 검사는 각 DB를 따로 읽어 클로드가 대조한다 |
| 날짜 컬럼명이 다르다 | `"출석 날짜"` 처럼 속성명을 그대로 쓰면 `no such column`. 반드시 `"date:<속성명>:start"` 로 쓴다. `:end`, `:is_datetime` 도 별도 컬럼이다 |
| relation은 등호 비교 불가 | `id`는 대시 있는 uuid인데, relation 값은 대시 없는 uuid를 담은 URL의 JSON 배열 문자열이다(예: `["https://app.notion.com/0123456789abcdef0123456789abcdef"]`). 두 DB의 id를 relation 값과 `=` 로 비교하는 조건은 절대 성립하지 않는다. `LIKE '%<대시 없는 uuid>%'` 로 부분 일치시키거나, 작은 DB를 통째로 읽어 클로드가 문자열에서 uuid를 뽑아 대조한다 |
| formula·rollup은 컬럼으로 조회 불가 | `성적(%)`, `보강 디데이`, `KPI 점수`, `수강료미납현황` 같은 수식·롤업 속성은 쿼리 결과에 나타나지 않는다. 이런 값이 필요한 검사는 원본 속성(점수·총점 등)을 따로 읽어 클로드가 계산한다 |
| 첨부 DB 10개 상한 | 한 쿼리에 11개 이상의 collection을 걸면 `too many attached databases - max 10`. JOIN을 안 쓰므로 보통 문제되지 않지만, 서브쿼리로 여러 DB를 참조할 때 유의한다 |

그 외에 확인된 것:
- `WEEKDAY()`, `TO_CHAR()`, `INTERVAL`, `CURRENT_DATE` 는 지원 여부가 확인되지 않았다. 쓰지 않는다. 요일 판정·날짜 연산은 SQL이 아니라 클로드가 값을 읽은 뒤 계산한다. 오늘 날짜나 cutoff 날짜가 필요하면 클로드가 실행 시점의 날짜로 계산해 리터럴 문자열로 쿼리에 넣는다
- **status 는 화면에 표시되는 문자열로 비교한다.** `수강료 납부` 의 `상태` 는 `"상태" = '미납'`, `신입생` 의 `상태` 는 `"상태" = '등록 완료'` 처럼 옵션 이름을 그대로 쓴다. 1·2단계부터 이 형태로 조회해 왔다 — checkbox 와 달리 별도 직렬화(`'__YES__'` 같은 것)가 관측된 적이 없다. 실측 확인: `수강료 납부` 에 `WHERE "상태" = '미납'` 을 걸어 8월 미납 3건이 정확히 반환됐다(2026-08-22). 다만 status 조건이 예상 밖으로 0행을 내면 그 DB 의 `상태` 를 조건 없이 한 번 읽어 실제 값 표기를 확인한다
- 체크박스 값은 `'__YES__'` / `'__NO__'` 문자열이다. `true`/`false` 가 아니다. **미체크는 NULL 이 아니라 `'__NO__'` 문자열로 온다** — `학생 과목별 페이지` 17행과 `출석부` 112행, 총 129행을 `typeof()` 로 전수 확인한 결과 NULL 은 한 건도 없었다. 따라서 `"<속성>" = '__NO__'` 로 그냥 비교하면 된다. 다만 `IS NULL` 을 함께 걸어도 결과는 같으므로 기존 쿼리를 굳이 고칠 필요는 없다

## formula·rollup 은 원본 값을 읽어 클로드가 계산한다

수식·롤업 속성은 조회 결과에 아예 나타나지 않는다. **그 속성을 SELECT 목록에 적으라고 지시하는 절차는 전부 잘못된 것이다.** 대신 원본 값을 읽어 클로드가 계산한다. 실제로 자주 필요한 것은 다음 셋이다.

| 필요한 값 | 실제 타입 | 대신 하는 일 |
|---|---|---|
| 시험의 `성적(%)` | formula | 시험 행의 `점수` 와 그 행이 가리키는 시험 카테고리의 `총점` 을 따로 읽어 `점수 ÷ 총점 × 100` 을 클로드가 계산한다 |
| 시험 카테고리의 `평균` | formula | 그 카테고리를 가리키는 시험 행들의 `점수` 를 모두 읽어 클로드가 평균을 낸다 |
| 학교의 `인원 수` | rollup | 그 학교를 가리키는 학생 행을 읽어 클로드가 센다 |

같은 이유로 `KPI 점수`, `최근성적`, `최근평균`, `수강료미납현황`, `보강 디데이`, `참여 요일 및 시간` 같은 속성도 직접 읽을 수 없다.

## relation 대조는 uuid 정규화가 먼저다

relation 값은 **대시 없는 uuid 를 담은 URL** 의 JSON 배열 문자열이다(예: `["https://app.notion.com/0123456789abcdef0123456789abcdef"]`). 반면 다른 DB 에서 읽어 온 `id` 에는 대시가 있다. 두 값을 그대로 비교하면 언제나 불일치한다.

대조 순서는 항상 같다.

1. 양쪽 DB 를 따로 조회한다(JOIN 이 없으므로 방법이 이것뿐이다)
2. 양쪽에서 uuid 만 뽑아 **대시를 제거해 정규화**한다
3. 정규화한 문자열끼리 비교한다

한쪽 DB 가 작고 다른 쪽이 큰 경우에는, 작은 쪽 uuid 를 먼저 얻어 큰 쪽 쿼리에 `LIKE '%<대시 없는 uuid>%'` 조건으로 넣는 편이 읽는 행 수를 줄인다.

## 날짜·연월은 표시되는 텍스트로 비교하지 않는다

`납부 월` DB 의 `납부 년월` 은 `2026년 1월` 처럼 **0 패딩이 없는 문자열**이다. 문자열 비교는 사전순이라 `'2026년 12월' < '2026년 5월'` 이 참이 된다. 이런 값에 `<`, `>`, `BETWEEN` 을 쓰면 결과가 틀린다.

값을 그대로 읽어 온 뒤 클로드가 연·월을 숫자로 파싱해 비교한다.

```sql
-- 틀림
SELECT url FROM "collection://<납부 월>" WHERE "납부 년월" < '2026년 5월'

-- 맞음: 전부 읽고 클로드가 파싱해 비교한다
SELECT url, "납부 년월" FROM "collection://<납부 월>"
```

`date` 타입 속성(`date:<속성명>:start`)은 `YYYY-MM-DD` 형식이라 문자열 비교가 안전하다. 텍스트·title 로 저장된 연월만 이 문제에 해당한다.

## 행이 많은 DB 는 통째로 읽지 않는다

출석부·과제·시험·수강료 납부처럼 학생 수 × 기간만큼 행이 늘어나는 DB 는 `SELECT` 로 전부 끌어오지 않는다. **클래스·기간·학생 단위로 좁혀 여러 번 조회한다.**

제작자 템플릿에서 수십 행이던 것이 학생 200명 학원에서는 수천 행이 된다. 지금 잘 도는 절차가 구매자 데이터에서 그대로 도는 것은 아니다.

- 건수만 필요하면 `COUNT(*)` 로 세고, 예시가 필요한 항목만 `LIMIT` 을 붙여 상세 조회한다
- 기간 조건은 클로드가 계산한 cutoff 날짜를 리터럴 문자열로 넣어 건다
- 학생·클래스 단위로 좁힐 때는 위의 uuid 정규화 절차로 얻은 uuid 를 `LIKE` 조건에 넣는다

행이 적은 DB(클래스·학교·납부 월·시험 카테고리·문자 양식처럼 학생 수와 무관하게 개수가 고정에 가까운 것들)는 통째로 읽어도 된다. 다만 **몇 행인지 문서에 고정 숫자로 적지 않는다.** 구매자마다 다르다.
