# 신규 등록

## 시작 전에 읽는다

- `../academy-core/references/db-map.md` — DB id 를 얻는다. `학교`·`신입생`·`학생`·`학생 과목별 페이지`·`클래스`·`수강료 납부`·`납부 월` 의 `collection://<uuid>` 가 전부 필요하다 — 일곱 쓰기 스킬 중 이 스킬만 이렇게 많은 DB 에 걸친다
- `../academy-core/references/write-gate.md` — 쓰기 관문 일곱 단계(되물음 → 사전 검증 → 미리보기 표 → 승인 → 쓰기 → 결과 보고 → 남은 항목 확인). 이 스킬은 이 절차를 그대로 따르되, 아래 「절차」에는 이 스킬 고유의 것만 적는다
- `../academy-core/references/name-resolution.md` — 동명이인 판정(생년월일·학교명 대조)과 클래스명 부분 일치 조회를 이 스킬의 중복 확인·클래스 배정에 그대로 재사용한다
- `../academy-core/references/query-limits.md` — 조회를 시작하기 전에 반드시 읽는다. JOIN 금지, `date:<속성>:start` 컬럼명, relation uuid 정규화, formula·rollup 조회 불가, 행이 적은 DB(학교·클래스·납부 월)는 통째로 읽어도 된다는 기준이 여기 있다
- `../academy-core/references/domain-rules.md` — 쓰기 불가 속성, 「과목 페이지 필수」 판정 기준
- `../academy-core/references/completeness-checks.md` — 필수·되물음·공란 허용 세 분류. 「신입생 등록」행이 이 스킬 전용이다
- `../academy-core/references/write-safety.md` — 쓰기 동작의 자율·승인 경계

`~/.academy/config.json` 이 없으면 즉시 멈추고 `academy-setup` 을 안내한다.

## 언제 쓰나

- "신입생 김민준 등록해줘. 중3, 수학이랑 영어, 월 30만원"
- "신입생 명단 세 번째 학생 등록시켜줘"

## 쓰는 속성

**템플릿에 노션 버튼 자동화가 이미 있다.** `신입생` 행의 `재원생 등록` 버튼을 누르면 그 행의 정보가 `학생` DB 로 그대로 넘어간다. `학생` 행에도 과목별 버튼(실측 확인: `국어`·`영어`·`수학`·`과학`)이 있어, 누르면 `학생 과목별 페이지` 행이 생기는 것으로 보인다 — **다만 이 과목 버튼이 정확히 무엇을 만드는지는 확인된 바 없다.** 버튼을 대신 누를 방법이 없으므로(MCP 로는 버튼 클릭을 실행할 수 없다) 이 스킬은 **버튼이 하는 일을 다시 만들지 않는다** — 버튼은 사람이 누르고, 클로드는 채우고 검증한다(`academy-message` 가 문자 발송 버튼을 대신 누르지 않는 것과 같은 경계, `../academy-core/references/write-safety.md` 「알림톡·문자 발송」 참고).

그래서 이 스킬이 직접 쓰는 것은 셋뿐이다: **신입생 행 채우기, (필요하면) 학교 행, 클래스 배정과 수강료 납부 행.** `학생` DB 에는 행을 만들지 않는다. 값 쓰기도 하지 않는 것이 원칙이고, 버튼이 `학생 전화번호`를 넘기지 못한 경우에만 건별 승인을 받아 그 한 칸을 채운다(아래 「버튼 결과 검증」).

**"학생 1명 등록에 행 3~6개"라는 규모감은 여전히 맞다** — 다만 그 행들이 전부 이 스킬의 `notion-create-pages` 호출로 생기는 것은 아니다. 학교(0~1)·신입생(1, 새로 만들거나 채움)·학생(1, 버튼)·과목 페이지(1~2, 버튼 또는 스킬)·수강료 납부(1~2, 스킬)를 합치면 시스템 전체에 생기는 행 수는 같은 범위다. 스킬이 미리보기·되돌리기에서 "내가 쓴 것"이라고 부르는 범위만 좁다.

**학교** (있으면 재사용하고 새로 쓰지 않는다. 대부분의 경우 아예 필요 없다 — 아래 「신입생」 참고)

| 속성 | 타입 | 값 |
|---|---|---|
| `학교명` | title | 학생이 다니는 학교 이름 |
| `선택` | select | `초등학교` / `중학교` / `고등학교` 중 하나 |

**신입생** (행이 이미 있으면 빈 칸만 채운다. 없으면 새로 만든다)

| 속성 | 타입 | 값 |
|---|---|---|
| `이름` | title | 이미 있으면 그대로, 새로 만들 때만 채운다 |
| `date:상담 날짜:start` | date | 이미 있으면 절대 건드리지 않는다. 새로 만들 때만 채운다(발화에 날짜가 없으면 오늘) |
| `date:생년월일:start` | date | 이미 있으면 건드리지 않는다 |
| `성별` | select | `남` / `여`. 이미 있으면 건드리지 않는다 |
| `학교` | relation → 학교 | **실측 7건 전부 이미 채워져 있었다.** 채워져 있으면 그대로 두고 절대 다른 학교로 덮어쓰지 않는다. 비어 있을 때만(드문 경우 — 원장이 상담 단계에서 학교를 못 받았을 때) 새로 확인해 채운다 |
| `학부모 전화번호` | phone_number | 이미 있으면 건드리지 않는다 |
| `학생 전화번호` | phone_number | 이 속성은 `신입생` DB 에 실제로 있다. 이미 있으면 그대로, 비어 있으면 원장에게 물어 채운다(중학생은 `completeness-checks.md` 공란 허용 대상이라 굳이 묻지 않아도 된다). 버튼이 이 값을 `학생` DB 로 그대로 넘긴다고 보고, 「버튼 결과 검증」에서 넘어왔는지 확인한다 |
| `특이사항` | text | 이미 있으면 건드리지 않는다 |
| `학년 수정` | number | 원장이 답한 학년(예: "중3" → `3`). 실측 7건 전부 이 칸만 공란이었다 — **이 칸이 비면 버튼이 넘겨도 학생 행에서까지 비게 된다.** 버튼을 누르기 전에 반드시 채운다. 생년월일로 계산되는 값(`학년` formula)과 다르면 이 값이 우선한다 |
| `상태` | status | **새로 만드는 행에만** 초기값을 정한다 — 원장에게 확인하고, 기본 제안은 `상담 전`이다(`completeness-checks.md` 「기본값을 제시하며 묻는다」와 같은 방식). 이미 있는 행은 건드리지 않는다 — 버튼이 등록 처리 시 이 값을 바꾸는지 미확인이므로(아래 「버튼 결과 검증」), 값이 이미 있으면 스킬이 먼저 손대지 않는다 |

**쓰지 않는 것.** `재원생 등록`(button)에는 애초에 값을 쓸 수 없다.

**학생 과목별 페이지** (수강 과목 수만큼)

| 속성 | 타입 | 값 |
|---|---|---|
| `이름` | title | `<학생명> <과목>` 형식(예: `박시우 영어`). 버튼이 만든 행이면 이미 채워져 있을 것이다. 스킬이 직접 만드는 경우에만 이 형식으로 채운다 |
| `학생` | relation → 학생 | 버튼이 만든 행이면 이미 채워져 있을 것이다. 스킬이 직접 만드는 경우에만 채운다 |
| `클래스` | relation → 클래스 | **버튼이 채우는지 미확인이다.** 조회해 비어 있으면 이 스킬이 채운다. 값이 이미 있으면(버튼이 채웠거나 다른 경로로 이미 배정돼 있으면) 그 값이 맞는지 원장에게 확인한 뒤에만 손댄다 |

**수강료 납부** (과목 페이지마다 1행, 전부 이 스킬이 직접 만든다)

| 속성 | 타입 | 값 |
|---|---|---|
| `수강료` | number | 원 단위 금액 |
| `상태` | status | `미납` |
| `납부 월` | relation → 납부 월 | 첫 청구월 url. 한 건이어도 배열로 감싼다 |
| `이름 붙여넣기` | relation → **학생 과목별 페이지** | 과목 페이지 url |

`date:<속성>:start` 표기는 조회·쓰기 양쪽 모두 그대로 쓴다. relation 은 대시 없는 uuid 가 아니라 **페이지 url 배열**을 넣는다.

**쓰지 않는 것.** 쓰기 불가 속성의 권위 목록은 `../academy-core/references/db-map.md` 「DB별 쓰기 불가 속성」이다. 이 스킬은 여섯 DB 에 걸치므로 그 표에서 `학교`·`신입생`·`학생`·`학생 과목별 페이지`·`수강료 납부`·`납부 월` 줄을 본다 — `학년`(학생·신입생, formula)만은 쓰기 경로가 따로 있어 `학년 수정`(number)에 넣는다.

표 밖에서 이 스킬이 추가로 쓰지 않는 것:
- `학생 과목별 페이지`의 `출석부`·`과제`·`시험`·`재원생 상담`·`수강료 납부`·`문자 양식`(전부 relation) — 수강료 납부 쪽의 `이름 붙여넣기`를 채우면 자동으로 맞춰진다. 과목 페이지 쪽에서 먼저 채우지 않는다
- `학생 과목별 페이지`의 `전송완료`(checkbox, 기본값 유지)
- `수강료 납부`의 title(빈 이름 속성) · `date:납부 날짜:start`(납부 완료 처리 전까지 비운다, `academy-tuition` 참고) · `비고`

## 절차

`write-gate.md` 일곱 단계를 그대로 따른다. 아래는 이 스킬 고유의 것만 적는다.

### 되물음을 한 번에 묶는다

버튼 클릭을 사람이 노션 화면에서 직접 해야 하므로 대화가 중간에 한 번 끊긴다(아래 「진행 순서」). 왕복을 줄이려면 **필요한 항목을 전부 첫 되물음에서 한 번에 받는다** — 필수 항목은 `write-gate.md` 1단계 표를 따르되, `completeness-checks.md` 「신입생 등록」행의 **첫 등원일**도 함께 받는다(첫 청구월을 정하는 근거가 된다 — 아래 「7. 클래스 배정 + 수강료 납부」). 나중에 필요한 것(학교·학년·학생 전화번호·수강료·신규 신입생이면 상태 초기값)도 미리 받아 두면 버튼 확인 후 재질문 없이 갈 수 있다.

### 사전 검증 (2단계) — 중복 확인이 급소

- **(가) 수업일 대조 — 적용하지 않는다.** 등록 자체는 특정 수업일에 종속되지 않는다.
- **(나) 중복 — `신입생` 의 `상태` 를 근거로 삼지 않는다.** `학생` DB를 이름으로 조회해 이미 있는지를 직접 확인하는 것이 유일하게 믿을 수 있는 판정이다. **`신입생` 행을 채우기 전에** 한다 — 이미 재원생인 사람의 신입생 행을 채우고 버튼까지 누르게 하면 중복 등록으로 이어진다.

  ```sql
  SELECT id, url, "이름", "date:생년월일:start", "date:퇴원 날짜:start" FROM "collection://<학생>" WHERE "이름" = '<이름>'
  ```

  **퇴원 여부까지 이 한 쿼리로 판정한다** — `date:퇴원 날짜:start` 를 SELECT 목록에서 빼면 아래 마지막 항목(퇴원 이력 있는 동명 학생)을 판정할 근거 자체가 없어져, 재등록 학생을 조용히 신규로 등록하게 된다.

  - 0행 — 새로 등록해도 된다.
  - 1행 이상이고 생년월일이 다르면 — 동명이인이다(`name-resolution.md` 「동명이인」과 같은 판정). 다른 사람이므로 새로 등록해도 된다.
  - 1행 이상이고 생년월일이 같으면 — **진짜 중복이다.** `신입생` 행을 채우지 않고 멈춰서 원장에게 확인한다. `신입생` 의 `상태`가 이미 `등록 완료`였든 아직 `상담 전`·`상담 중`이었든 결과는 같다 — **`상태` 값과 무관하게 `학생` DB 조회 결과가 우선한다.**
  - `신입생` 의 `상태`가 이미 `등록 완료`인데 `학생` DB 조회가 0행이면 — 상태 표시와 실제 등록 여부가 어긋난 것이다(둘 중 무엇이 원인인지는 이 스킬이 판정하지 않는다). 중단하지 않고 정상적으로 등록을 진행하되, 이 불일치를 미리보기에 한 줄 알린다.
  - 생년월일이 같은 행의 `date:퇴원 날짜:start` 에 값이 있으면(퇴원 처리된 행) 재등록 판단이 필요하다 — 이 스킬은 재등록 절차를 정의하지 않으므로, 진행하지 말고 원장에게 어떻게 할지 확인한다.
- **(다) 직전 과제 — 해당 없음.** `academy-homework` 전용이다.
- **(라) 퇴원 검증 — 해당 없음.** 신규 등록 학생은 아직 퇴원 이력이 없다. 위 (나)에서 퇴원 이력이 있는 동명 학생을 만나는 경우는 재등록이지 이 항목의 대상이 아니다.

### 진행 순서

**1. 신입생 확인.** 이름으로 `신입생` DB를 조회한다.

```sql
SELECT id, url, "이름", "상태", "date:상담 날짜:start", "date:생년월일:start", "성별", "학교", "학부모 전화번호", "학생 전화번호", "특이사항", "학년 수정" FROM "collection://<신입생>" WHERE "이름" = '<이름>'
```

- 1행이고 `학교`가 이미 채워져 있으면(실측 7건 전부 이 경우다) 그 값을 그대로 쓴다 — 아래 「2. 학교」를 건너뛴다.
- 0행이거나, 1행인데 `학교`가 비어 있으면(드문 경우) 「2. 학교」로 간다.

**2. 학교 (필요할 때만).** 학교명이 원장 발화에 있으면(또는 위 1단계에서 새로 물어봤으면) 학교 DB를 먼저 조회한다(행이 적으므로 통째로 읽는다).

```sql
SELECT id, url, "학교명", "선택" FROM "collection://<학교>"
```

읽은 학교명과 원장이 말한 이름을 클로드가 대조한다(줄여 말한 경우 포함 — `name-resolution.md` 「클래스명 부분 일치」와 같은 방식으로 판단한다). 일치하는 행이 있으면 그 url을 재사용하고 새로 만들지 않는다. 없으면 새로 만든다 — `선택`은 학교명에 `초등학교`·`중학교`·`고등학교`가 그대로 포함돼 있으면 그것으로 정하고, 애매하면 원장에게 확인한다. **새로 만들 학교는 바로 쓰지 않는다** — 아래 「3. 신입생 행 채우기/생성」의 미리보기 1에 함께 올리고, 승인 후에만 만든다.

**3. 신입생 행 채우기/생성 (첫 번째 쓰기).**

- 1단계에서 0행이었으면 — 완전히 새로운 유입이다. `notion-create-pages` 로 새 `신입생` 행을 만든다(「쓰는 속성 → 신입생」표 전부 채운다. `상태` 초기값도 포함한다).
- 1단계에서 1행이었으면 — `notion-update-page` 를 `command: "update_properties"` 로 호출해 **비어 있는 칸만 채운다.** 이미 값이 있는 칸(이름·상담 날짜·생년월일·성별·학교·학부모 전화번호·특이사항·상태 — 실측 7건은 `학년 수정` 딱 하나만 비어 있었다)은 원장이 명시적으로 고치라고 하지 않는 한 properties 에 넣지 않는다 — 생략하면 유지된다.

**미리보기 (신입생, 학교를 새로 만드는 경우 함께 올린다)**를 보여주고 승인받은 뒤 쓴다.

```
신입생 「김민준」 행을 만들고 다음 값을 채웁니다.

| 이름 | 생년월일 | 성별 | 학교 | 학부모 전화번호 | 학생 전화번호 | 학년 수정 | 상태 |
|---|---|---|---|---|---|---|---|
| 김민준 | 2011-05-02 | 남 | 해솔중학교 | 010-1234-9001 | (없음) | 3 | 상담 전 |

이대로 채울까요?
```

**표의 값끼리 서로 맞는지가 원장이 이 화면에서 가장 먼저 볼 것이다.** 2011년생은 2026년 기준 중3이고, 학교도 중학교여야 하고, `학년 수정` 3 은 그 중3을 가리킨다 — 셋 중 하나라도 어긋나면(예: 고등학교에 `학년 수정` 3) 버튼이 그대로 학생 DB 로 넘겨 학년이 틀린 채 굳는다. 이 예시의 나머지 흐름은 `references/examples.md` 예시 1 과 같은 값이다.

학교를 새로 만들어야 하는 경우에는 첫 줄에 "학교에 1건(<학교명>, <선택>)을 새로 만들고" 를 앞에 붙이고 표의 학교 칸에 "(신규)" 를 표시한다 — `references/examples.md` 예시 3(이도윤·다솜고등학교)이 그 형태다.

**4. 버튼 안내 (쓰기 아님).** 승인·쓰기가 끝나면 원장에게 버튼을 눌러 달라고 안내하고 응답을 기다린다. 스킬이 이 시점에 학생 행을 만들지 않는다.

> 신입생 행을 채웠습니다. 노션에서 그 행의 `재원생 등록` 버튼을 눌러 주세요. 누르면 정보가 학생 DB 로 넘어갑니다. 다 되면 알려 주세요.

**5. 버튼 결과 검증 (읽기).** 원장이 눌렀다고 답하면 학생 DB를 이름으로 조회해 행이 실제로 생겼는지, 값이 넘어왔는지 확인한다.

```sql
SELECT id, url, "이름", "date:생년월일:start", "성별", "학교", "학부모 전화번호", "학생 전화번호", "특이사항", "학년 수정" FROM "collection://<학생>" WHERE "이름" = '<이름>'
```

- 0행이면 버튼이 아직 안 눌렸거나 실패한 것이다. 그렇게 보고하고 다시 확인해 달라고 안내한다 — 이 스킬이 대신 학생 행을 만들지 않는다.
- 1행이 나왔는데 값 일부가 신입생 행과 다르면(비어 있거나 다른 값이면) 무엇이 안 넘어왔는지 원장에게 알린다. **`학생 전화번호`가 신입생 행에는 있는데 학생 행에 안 넘어왔으면** — 이 하나만 예외적으로 스킬이 직접 채운다(건별 승인). `notion-update-page` 를 `command: "update_properties"` 로 호출해 이 속성 하나만 넣는다: "학생 전화번호가 버튼으로 안 넘어왔습니다. 지금 채울까요?"
- `상태`가 `등록 완료`로 바뀌었는지도 함께 확인한다. **바뀐 경우와 안 바뀐 경우 둘 다 있을 수 있다.** 바뀌지 않았으면 스킬이 대신 바꾸지 않는다 — 버튼의 정확한 동작 범위가 확인되지 않았으므로, 바뀌지 않았다는 사실만 원장에게 알리고 바꿀지는 물은 뒤에만(건별 승인) 고친다.

**6. 학생 과목별 페이지 판정 (쓰기 아님).** 수강 과목마다 경로를 정한다. 과목 단어가 버튼 이름(`국어`·`영어`·`수학`·`과학`)과 정확히 같으면 그 버튼을 먼저 시도한다.

> 학생 행의 `<과목>` 버튼을 눌러 주세요.

버튼을 눌렀다고 하면(또는 버튼 이름과 안 맞아 애초에 시도하지 않았으면) 이 학생의 과목 페이지를 전부 조회해 확인한다.

```sql
SELECT id, url, "이름", "학생", "클래스" FROM "collection://<학생 과목별 페이지>" WHERE "학생" LIKE '%<5단계에서 확인한 학생 대시 없는 uuid>%'
```

**정확한 title 형식은 미확인이므로 `이름 = '<학생명> <과목>'` 같은 정확 일치로 조회하지 않는다** — 그 학생의 과목 페이지를 전부 읽어, 이번 과목에 대응하는 행이 있는지 클로드가 눈으로 대조한다. 정확 일치로 조회하면 버튼이 다른 형식으로 이름을 지었을 때 0행이 나와 같은 과목 페이지를 중복으로 또 만들게 된다.

- 대응하는 행이 있으면(버튼이 만들었거나 이전 단계에서 이미 있으면) 재사용한다 — 새로 만들지 않는다.
- 대응하는 행이 없으면 — 과목이 버튼 4개(국어·영어·수학·과학)에 없거나(실측에 `물리`처럼 이 넷에 없는 과목이 있다), 버튼을 시도했는데 안 생긴 것이다. **이 스킬이 직접 만들어야 한다는 뜻이지만, 아직 쓰지 않는다** — 7단계 미리보기에 "새로 만든다"로 올리고, 승인 후에만 만든다.

**7. 클래스 배정 + 수강료 납부 (두 번째 쓰기 — 6단계에서 직접 만들기로 정한 과목 페이지도 여기서 함께 쓴다).** 클래스는 이름으로 부분 일치 조회한다.

```sql
SELECT id, url, "클래스명" FROM "collection://<클래스>" WHERE "클래스명" LIKE '%<원장이 말한 클래스 조각>%'
```

**클래스는 기존 것만 배정한다. 이 스킬은 새 클래스를 만들지 않는다.** 조회가 0행이면 클래스명을 다시 확인하거나 원장에게 정확한 반 이름을 묻는다. 2행 이상이면 어느 반인지 되묻는다. 원장이 답한 과목 단어와 배정 클래스의 과목이 서로 다르면(예: 과목은 "수학"인데 클래스는 "고2 영어 내신반") 미리보기 전에 확인한다.

수강료 납부는 과목 페이지마다 1행, `상태`는 항상 `미납`으로 시작한다. 금액은 학생·과목마다 다를 수 있으므로 추측하지 않고 매번 확인한다(`academy-tuition` 이 같은 이유로 금액을 매번 묻는 것과 같다). 첫 청구월은 1단계 되물음에서 받은 **첫 등원일**을 근거로 정한다(첫 등원일과 청구 시작월이 어긋나면 원장에게 확인한다 — 정확한 일할 계산 정책까지 이 스킬이 자동으로 정하지 않는다). 정한 청구월로 `납부 월` DB에서 찾고, 없으면 만든다 — 찾고 만드는 방식은 `academy-tuition` 의 「납부 월 찾기·만들기」와 같다.

```sql
SELECT id, url, "납부 년월" FROM "collection://<납부 월>"
```

**미리보기 (학생 과목별 페이지·클래스·수강료)**를 DB 별로 나눠 보여주고 승인받은 뒤 쓴다. 이 미리보기 이전에는 학생 과목별 페이지를 직접 생성하는 `notion-create-pages` 호출을 하지 않는다.

```
납부 월에 1건(2026년 9월)을 만들고, 학생 과목별 페이지 2건에 클래스를 배정하고(2건 모두 버튼이 이미 만듦), 수강료 납부에 2행을 만듭니다.

| 이름(과목 페이지) | 출처 | 클래스 |
|---|---|---|
| 김민준 수학 | 버튼이 생성 | 중3 수학 정규 |
| 김민준 영어 | 버튼이 생성 | 중3 영어 내신반 |

| 이름 붙여넣기 | 수강료 | 상태 | 납부 월 |
|---|---|---|---|
| 김민준 수학 | 300,000 | 미납 | 2026년 9월 |
| 김민준 영어 | 300,000 | 미납 | 2026년 9월 |

이대로 진행할까요?
```

**`수학`·`영어` 는 둘 다 버튼이 있는 과목이라 「출처」가 둘 다 `버튼이 생성` 이다.** 6단계 버튼 목록(`국어`·`영어`·`수학`·`과학`)에 있는 과목을 이 표에서 `스킬이 새로 생성` 으로 적으면 안 된다 — 버튼이 만든 행과 스킬이 만든 행이 겹쳐 허브 DB(`학생 과목별 페이지`)에 같은 학생·같은 과목 행이 둘 생긴다. 행을 지우는 도구가 없어 되돌리려면 페이지 이동뿐이고, 그 사이 출결·과제·시험 relation 이 두 행으로 갈린다. **`스킬이 새로 생성`** 은 버튼 넷에 없는 과목(예: `물리`)일 때만 쓴다 — 그 형태는 `references/examples.md` 예시 5(장태윤 수학+물리)에 있다.

30행 기준·요약 형식은 `write-gate.md` 3단계를 그대로 따른다 — 이 스킬은 한 번에 30행을 넘는 경우가 거의 없지만 원칙은 같다.

### 부분 실패

이 스킬의 실패 지점은 두 군데다. 어느 쪽이든 조용히 넘어가지 않고, **이미 만든 것을 즉시 나열해 보고**한 뒤 어떻게 할지 묻는다.

1. **버튼을 눌렀다는데 학생 행이 안 생겼다(또는 값이 안 맞다).** 「5. 버튼 결과 검증」에서 잡는다. 스킬이 대신 학생 행을 만들지 않는다 — 노션에서 버튼을 다시 확인해 달라고 안내하고 대기한다. 이 시점까지 스킬이 실제로 쓴 것은 `학교`(새로 만들었다면)와 `신입생` 행뿐이다. 되돌릴 필요는 없다 — 둘 다 유효한 상태고, 버튼을 다시 누르면 이어갈 수 있다.
2. **7단계 승인 후 쓰기 도중 일부가 실패했다.** 예: 2과목 중 1과목만 끝나고 나머지가 실패. 성공한 것과 실패한 것을 각각 나열해 보고하고, 되돌릴지 실패한 부분만 재시도할지 묻는다.

되돌릴 때는 **생성분과 수정분을 다르게 다룬다.** 두 갈래의 정의·절차·승인 경계는 `../academy-core/references/write-gate.md` 6단계 「되돌리기는 생성분과 수정분 두 갈래다」에 있다 — 여기서는 이 스킬의 무엇이 어느 갈래인지만 적는다. 하나로 뭉뚱그려 전부 페이지 이동으로 처리하면 relation 수정까지 페이지째 옮기게 되어 사고로 이어진다(아래 「주의」참고).

- **생성분** — 수강료 납부 행, 스킬이 직접 만든 과목 페이지, 신규 학교 행, 새로 만든 `납부 월` 행.
- **수정분** — 신입생 행의 빈 칸 채움, 과목 페이지의 `클래스` relation 갱신, 드물게 있었던 학생 전화번호 보완, 건별 승인으로 바꾼 신입생 `상태`.

**수정분을 빈 값으로 되돌리지 않는다.** 원래 값이 있었으면 **그 원래 값으로** 되돌리고, 원래도 비어 있던 칸만 빈 값으로 되돌린다 — 특히 과목 페이지의 `클래스` relation 은 버튼이나 다른 경로로 이미 값이 있었을 수 있고(「쓰는 속성」의 `클래스` 줄), 그것을 공란으로 만들면 원래 배정이 사라진다. 그래서 이 스킬은 **바꾸기 전에 그 칸의 값을 먼저 읽는다** — 6단계 과목 페이지 조회가 `클래스` 를 SELECT 하는 이유가 이것이기도 하다.

**버튼이 만든 학생 행·과목 페이지 행은 어느 쪽으로도 되돌리기 대상이 아니다** — 스킬이 쓴 것이 아니라 노션 자동화의 산출물이다. 지워야 한다면 원장이 노션에서 직접 처리해야 한다.

## 주의

- 쓰기 절차·배치 상한(100건)·되돌리기는 `../academy-core/references/write-gate.md` 4~6단계를 따른다. **되돌리기의 생성분/수정분 두 갈래는 거기 6단계에 core 규칙으로 있다** — 이 스킬의 무엇이 어느 갈래인지는 「부분 실패」에 있다. 버튼이 만든 학생 행·과목 페이지 행은 어느 쪽으로도 되돌리기 대상이 아니다.
- 이 스킬은 클래스를 새로 만들지 않는다. 배정할 반이 아직 없으면(신규 개설반) 원장에게 먼저 `클래스` DB에 반을 만들어 달라고 안내한다 — 클래스 생성은 이 스킬의 범위 밖이다.
- 같은 발화에 수강료 관련 요청이 더 있어도(예: "형제 할인 적용해줘") 이 스킬이 이미 수강료 납부까지 만들었다면 그 추가 조정은 `academy-tuition` 의 「개인 납부 완료 처리」 영역이다 — 방금 만든 행을 기존 행 수정으로 넘긴다.
- **학생 행만 만들어지고 과목 페이지가 0개인 상태로 대화를 끝내지 않는다.** 이 스킬은 사람의 버튼 클릭을 두 번(등록 버튼, 과목 버튼) 필요로 해 대화가 끊기기 쉽다. 과목 버튼 단계에서 대화가 끊기면 `domain-rules.md` 「과목 페이지 필수」가 가리키는 상태(학생이 시스템에 나타나지 않는다)가 된다 — 중단하게 되면 그 상태임을 명시적으로 알리고 마무리한다.
